# Local PII Masker MVP要件定義

## 1. 文書情報

| 項目 | 内容 |
| --- | --- |
| 対象 | Local PII Masker MVP |
| ステータス | 初版 |
| 対象プラットフォーム | PC向けWebアプリケーション |
| 主対象言語 | 日本語 |
| データ保持方式 | 既定はブラウザメモリ内のみ。明示保存時はマスク対応表だけを暗号化してOPFSへ保存 |
| 関連詳細要件 | [マスキング前テキスト正規化 追加機能要件](text-normalization-requirements.md) |

## 2. 背景

生成AIなどの外部サービスへ業務テキストを入力する際、氏名、住所、組織名、電話番号、メールアドレス、社内固有名詞などを事前に除去または置換する必要がある。

手作業による置換では、見落とし、置換漏れ、表記揺れ、対応関係の管理負荷が発生する。本アプリは、ブラウザ内で候補検出と可逆マスキングを行い、外部へ渡すテキストから個人情報・機密情報を除去しやすくする。

## 3. MVPの目的

1. 日本語の長文テキストからマスク候補を自動検出できること
2. ユーザーが候補を確認、無効化、削除、手動追加できること
3. 原文を壊さず、同じ設定から一貫したマスク結果を生成できること
4. 原文とマスク結果を比較して、マスク漏れを確認できること
5. 外部サービスなどで処理したマスクを含む文章をローカルで復元できること
6. 既定ではユーザーデータを永続保存せず、ユーザーが明示的に保存した場合だけマスク対応表を暗号化してOPFSへ保存すること

## 4. MVPの対象外

- ユーザー登録、ログイン
- サーバーへの原文・対応表の保存
- LocalStorage、SessionStorage、IndexedDBへのユーザーデータ保存
- 自動保存、保存期限の指定、自動削除
- 端末間同期、チーム共有
- 暗号化ファイルの入出力
- 外部生成AIとのAPI連携
- スマートフォン、タブレットの正式対応
- ユーザーが任意の出現箇所を個別に選択して管理する機能（自動検出の曖昧姓に対する限定的な文脈判定は含む）
- マスク結果の直接編集
- AIによって削除・改変された情報の意味的な復元
- 法令上の匿名加工情報を生成したことの保証

## 5. 想定利用者

- 生成AIへ入力する文章から個人情報を除去したい利用者
- 顧客対応、障害報告、議事録、仕様書などを外部サービスへ渡す前に確認したい利用者
- 日本語テキストをPC上で処理する利用者

| 項目 | MVP方針 |

| 端末 | PC |

## 7. 用語

| 用語 | 定義 |
| --- | --- |
| 原文 | ユーザーが入力または貼り付けた、マスク前のテキスト |
| マスク対象 | 原文内でトークンへ置換する文字列 |
| マスクトークン | マスク対象を置換する識別用文字列 |
| マスク結果 | 原文と有効なマスク対象一覧から生成したテキスト |
| 復元 | マスクを含む文章に残っているマスクトークンを、対応する復元文字列へ置換する処理。検出補正が適用された対象は補正後文字列へ、それ以外の対象は原文表記へ置換する |
| 復元文字列 | トークン復元時に挿入する文字列。検出用正規化を経た候補では、実際に検出が成立した正規化後の一致範囲から確定し、補正のない候補と手動追加候補では原文表記を使用する |
| 自動検出候補 | 正規表現またはNERで検出され、有効なマスク対象として追加される候補 |
| セッション | ページを開いてから、再読み込みまたはタブを閉じるまでの利用単位 |

## 8. 基本利用フロー

1. ユーザーが原文を入力または貼り付ける
2. アプリが正規表現とローカルNERで候補を検出する
3. ユーザーが自動的に有効化された対象を確認し、不要な対象を無効化または削除する
4. 必要に応じて原文上の文字列を手動追加する
5. アプリが原文とマスク対象一覧からマスク結果を生成する
6. ユーザーが「原文」と「マスク結果」を切り替えて確認する
7. ユーザーがマスク結果をコピーし、外部サービスへ渡す
8. ユーザーがマスクを含む文章をアプリへ貼り付ける
9. アプリが文章内の既知のマスクトークンを対応する復元文字列へ置換する
10. ユーザーがマスクを復元した文章を確認してコピーする

## 9. 機能要件

### FR-01 原文入力

- 長文テキストを入力または貼り付けできること
- 原文は編集可能であること
- 文字数と30,000文字の入力上限を表示すること
- 30,000文字を超える入力・貼り付けは受け付けず、既存の原文を保持すること
- 原文をURL、クエリパラメータ、ブラウザ履歴へ含めないこと

### FR-02 自動検出の実行

- ユーザー操作により自動検出を開始できること
- 自動検出が1秒以上継続する場合は、候補一覧へ反映されるまでスピナー付きの共通進行状態を表示すること。1秒未満で切り替わる途中フェーズは表示しないこと
- 正規表現による検出とNERによる検出を統合できること
- 検出処理中も画面操作が著しく停止しない構成を目標とすること
- 検出失敗時は原文と既存設定を保持したまま、エラーを表示すること
- Phase 2では、NERが未実装または未利用でも、正規表現・検査ロジックによる形式検出だけで自動検出を完了できること
- Phase 2の自動検出は、原文、既存の手動追加項目、既存候補を破壊せず、候補統合結果だけを追加または更新すること
- Phase 3では、同じ自動検出操作で形式検出とローカルNERを連続実行し、両方の候補を統合できること
- Phase 3では、NERモデルの取得・初期化・推論に失敗しても、形式検出で得られた候補を保持し、手動追加を継続できること

### FR-03 正規表現・検査ロジックによる検出

MVPの初期対象候補は以下とする。

- メールアドレス
- 電話番号
- 郵便番号
- `http://`または`https://`で始まるURL
- IPv4アドレスおよびIPv6アドレス
- `ユーザーID`、`ログインID`、`パスワード`等の明示ラベルに続く認証情報
- `生年月日`、`誕生日`、`DOB`等の明示ラベルに続く日付
- 市区町村と丁目・番地・号等を含む日本語住所

Phase 2で正式に実装するカテゴリと扱いは以下とする。

| 検出対象 | 登録カテゴリ | 検出方針 |
| --- | --- | --- |
| メールアドレス | `EMAIL` | 一般的な `local-part@domain` 形式に加え、`@`前後に半角または全角空白が入った表記を対象とし、末尾の句読点や括弧を候補に含めない |
| 電話番号 | `PHONE` | 日本国内で一般的な固定電話、携帯電話、フリーダイヤル等の数字列と区切り記号を対象とする |
| 郵便番号 | `POSTAL_CODE` | `123-4567`、`〒123-4567` 相当の形式を対象とする |
| URL | `OTHER` | `http://`または`https://`で始まるASCII URLを対象とし、末尾の句読点や日本語本文を候補に含めない |
| IPアドレス | `OTHER` | IPv4の各オクテットとIPv6の完全・圧縮表記を検証し、URL内ではURL候補へ一本化する |
| ユーザーID・パスワード | `SECRET` | 明示ラベル直後の引用値、またはコロン・イコール・空白で区切られたASCII値を対象とし、ラベル自体は候補に含めない |
| 生年月日 | `OTHER` | 明示ラベル直後の西暦・和暦日付を実在日と元号期間で検証し、年月日の値だけを候補にする |
| 日本語住所 | `ADDRESS` | 市区町村に続いて丁目・番地・号またはハイフン区切りの地番がある文字列を対象とし、空白後の建物名・階数を可能な範囲で含める |

検出時の共通ルールは以下とする。

- 検出した文字列は原文上の表記を保持し、候補統合とマスキングは既存のNFC正規化・完全一致ルールに従うこと
- 検出専用テキスト上で空白等を除去した場合は、検出範囲を位置マッピングによって原文上の連続範囲へ戻し、候補文字列には原文の表記を使用すること
- 半角・全角の数字やハイフンを検出対象に含める場合でも、候補文字列を別表記へ変換しないこと
- 前後に付いた句読点、閉じ括弧、引用符など、PII本体ではない可能性が高い文字は候補から除外すること
- 生年月日の明示ラベルがない一般日付、および認証情報の明示ラベルがない各種識別番号候補は現時点では実装対象外とすること
- 正規表現候補の初期状態は「有効」とし、検出直後からマスク結果へ反映すること
- 正規表現検出を再実行しても、同じ文字列の候補を重複作成しないこと
- 既存項目と同じ文字列が検出された場合、既存項目へ検出元`regex`を追加し、ユーザーが設定したカテゴリと有効・無効状態を優先すること

以下は追加候補とし、誤検出率を確認して採用を判断する。

- 文脈ラベルのない一般日付
- 各種識別番号候補

正規表現に一致した文字列は有効なマスク対象として候補一覧へ追加する。ただし、形式だけで個人情報だと保証せず、ユーザーが検出元を確認して不要な対象を無効化できるようにする。

Phase 3では、NERで漏れやすい基本的な姓名を補うため、既存の文脈付き人名補助検出に加えて、漢字列に敬称または役職接尾辞が直接続く表記を文脈に関わらず候補化する。対象は1〜20文字の漢字列＋敬称とし、一般的な姓リストにない`鬼頭さん`、`鬼頭君`のような表記も含める。同一文節内で読点区切りに連続する敬称付き名称も個別に候補化する。ただし、`仕様`・`既存仕様`・`検出仕様`のように敬称の文字と一致することが明らかな一般語は除外する。敬称単独、敬称直後に漢字が続くため境界を確定できない表記は候補にしない。英語氏名は、明示的な人名ラベル、構造化人名フィールド、またはNERの`PER`結果である場合だけ自動候補にする。文脈のない英単語2語は形式検出せず、NERが`PER`として返さない場合は手動追加で対応する。

日本語姓辞書は、検出ロジックから分離した配列データとして管理し、正規化後の重複を除いた200姓以上を収録する。辞書から生成する照合パターンは姓の長い順、同長は安定した順序とし、正規表現へ姓文字列を直接埋め込まない。`髙橋`、`渡邉`、`渡邊`、`齋藤`、`齊藤`、`濱田`、`𠮷田`などの異体字は照合時に代表字へ正規化するが、候補文字列とマスク範囲は原文表記を保持する。`林`、`森`、`原`、`東`、`南`、`関`、`堀`、`岡`、`辻`などの曖昧姓は、敬称または明示的な人名ラベル・姓名文脈がある場合に限り姓単独候補として扱い、一般語中の一致は候補にしない。姓辞書には将来の頻度・信頼度・外部辞書由来情報を追加できる型を用意するが、外部大規模辞書は導入しない。

人名・組織名候補の直後に敬称または役職が連続する場合は、その接尾辞を含む原文範囲を一つのマスク対象として登録する。対象は`さん`、`様`、`殿`、`氏`、`先生`、`君`、`くん`、`ちゃん`、`御中`、`貴社`、`御社`、`貴行`、`御行`、`貴院`、`御院`、`貴校`、`御校`、`貴庁`、`御庁`、`貴法人`、`御法人`、`相談役`、`顧問`、`最高経営責任者`、`CEO`、`会長`、`社長`、`副社長`、`専務`、`常務`、`監査役`、`執行役員`、`理事`、`理事長`、`本部長`、`事業部長`、`部長`、`次長`、`部長代理`、`室長`、`課長`、`参事`、`主幹`、`係長`、`主任`、`チーフ`、`リーダー`、`マネージャー`とする。候補の前後にある句読点・助詞は含めず、敬称だけの文字列や境界なく後続文字へ連結する表記は候補にしない。候補範囲が原文上で確定できない場合は、誤った出現箇所を選ばず従来候補を保持する。

姓名間の半角・全角空白は原文どおり候補に含める。一般的な姓と1〜4文字の漢字名が空白で明確に区切られている場合は、文脈語がなくても有効な対象として補助検出する。漢字名が1文字で終端したように見えても、同一行で直後に半角または全角空白と漢字1文字が続く場合は、OCR由来の分断として氏名全体を原文表記のまま候補化する。AIが一般姓を持つ3〜7文字の漢字姓名を検出した場合は、その姓名の各文字間に半角または全角空白が0〜1文字入り、空白除去後に同じ姓名となる原文中の表記も形式候補として補完する。補完対象は少なくとも1文字の空白を含み、前後が漢字に直結しない表記に限定し、空白2文字以上、タブ、改行は文字間区切りとして扱わない。1件以上の検出済みフルネームから得た2文字以上の一般的な姓が原文中に独立して出現する場合は、姓単独の候補を補完する。姓候補は他の自動検出候補と同様に初期有効とする。一括モードでは同一文字列の全箇所をマスクするため、同じ姓から始まる非人名複合語内も置換対象とする。文脈付きモードでは、曖昧な一文字姓に限り専用の一般語パターン辞書に一致した出現箇所を除外する。姓候補専用の複合語警告は表示しない。1文字姓は通常文から自動派生しないが、番号付き・箇条書きの名簿項目では、曖昧姓であっても単独候補として検出する。検出済みフルネームの姓が原文中に独立して存在し、同じ姓を持つ別の4〜7文字の姓名がMarkdownの単一値コードブロックに記載されている場合は、その別姓名を補完したうえで姓単独も候補化する。

Phase 6では、OCRで姓名間に単一改行が入った表記を形式検出とNER用テキストの両方で結合する。前行末と次行先頭の漢字列が各1〜3文字で、前側が行頭または区切り文字に接し、句読点・空行を挟まず、Markdown見出し・コードブロック外である場合に限定する。また、3〜7文字の漢字・カタカナが各文字間の半角または全角空白1文字で完全に分割された表記と、一般姓で始まり文字間空白が2か所以上ある`山 田　太郎`等の混在表記は空白を除去する。一般姓で始まる漢字姓名は形式候補として直接登録し、正規化テキストはNERにも渡す。単語間空白1個、連続空白、タブ、改行、前後が漢字・カタカナに直結する部分範囲は対象外とする。候補は改行と周辺空白を含む原文上の連続範囲へ戻し、候補文字列とマスクには原文表記を使用する。

検出用正規化を経て成立したマスク対象は、候補表示、原文ハイライト、出現数計算、マスク範囲には補正前の原文表記を使用し、トークン復元時には検出が成立した補正後文字列を使用する。対象となる補正には、`fullwidth_ascii`、`hyphen_variants`、`email_at_spacing`、`japanese_inter_character_space`、`email_line_break`、`url_line_break`、`line_end_hyphen`、`phone_line_break`、`address_line_break`、`person_name_line_break`、`organization_line_break`を含む。複数の補正が適用された場合は、検出パイプラインが実際に生成した最終的な正規化後の一致範囲を一つの復元文字列として保持し、復元時に個別ルールを再適用しない。補正ルールを持たない自動候補と手動追加候補は、原文表記を復元文字列とする。複数の既知トークンや同一トークンの複数出現も、それぞれ同じ規則で決定論的に復元する。

Phase 6の構造化PIIでは、メール・URLが複数の構造記号または行末ハイフン位置で単一改行している場合に、改行だけを除去して検出する。行末ハイフン自体は保持する。住所は都道府県、市区町村、町域、丁目・番地・号等の構成要素の境界に加え、丁目から番、番から号の間にある単一改行を除去し、完全な住所形式になる範囲だけを候補化する。空行、通常文、Markdown見出し・コードフェンス・水平区切りをまたいで結合しない。正規化を経た候補は、候補カードへ適用した補正内容を日本語ラベルで表示する。

Markdown表またはCSVの`氏名`・`名前`・`Name`・`full_name`列、`司会:`・`記録:`・`担当:`・`Owner:`等のキー値行、妥当なJSONの`manager`・`reviewer`・`developer`・`designer`等の既知フィールドでは、値領域に限定して姓名を補助検出する。構造化フィールド内では一般姓を持つ漢字姓名と、各語がTitle Caseまたは全大文字の空白区切り英語氏名を対象にする。不正JSON、人名列のない表、文脈のない一般漢字列・英単語列は対象にしない。

日本語住所のルール検出は見逃し補助であり、住所であることを保証しない。番地表現のない地名だけの文字列は候補にせず、NERの`LOC`・`INS`候補と相互補完する。

`自宅住所`、`登録住所`、`配送先`、`住所`、`所在地`、`送付先`と、それに続く`は`、コロン、空白は文脈ラベルとして扱い、住所候補文字列に含めない。

### FR-04 ローカルNERによる検出

- Transformers.jsを実行基盤として使用すること
- ONNX形式の日本語NERモデルをブラウザ内で実行すること
- 初期対象カテゴリは、人名、地名・住所、組織名とすること
- AIモデルの出力は有効なマスク対象として提示し、検出元と信頼度を確認して不要な対象を無効化できること
- 信頼度を取得できる場合は参考情報として表示すること
- MVP採用モデルとして`jiting/xlm-roberta-ner-japanese_onnx`を使用すること
- `PER`は`PERSON`、`ORG`、`ORG-P`、`ORG-O`は`ORGANIZATION`、`LOC`と`INS`は暫定的に`ADDRESS`、`PRD`と`EVT`は`OTHER`へ写像すること
- 英語氏名は文脈のない表記でも、モデルが原文上の完全一致範囲を`PER`として返した場合は`PERSON`候補として維持すること
- モデル出力に原文上の位置が含まれる場合は、モデルの`word`ではなく原文の該当範囲を候補文字列として使用すること
- NER候補は原文に完全一致する文字列だけを新規候補にすること
- 1文字候補、短い英数字だけの候補、メールアドレス・URL・形式検出済み住所・構造から検出済みフルネーム内に含まれる部分文字列候補は、過検出抑制のため候補から除外すること
- 一覧行、箇条書き、Markdown表セルで、一般姓から始まる漢字姓名の直後に4～12文字のひらがな読みが連結する場合は、漢字姓名だけを形式候補として補完すること
- 氏名直後の読み仮名内で分割された組織・住所NER候補、形式検出済みメール・URL・住所・電話番号内の異なる部分文字列NER候補、より長い同カテゴリ候補に包含される組織・住所NER候補、階数・号室だけの住所NER候補は除外すること
- 電話番号候補に包含される郵便番号候補は除外すること。単独で存在する3桁-4桁表記は郵便番号候補として維持すること
- 電話番号の数字・ハイフン間に単一改行が入った場合は、検出用テキスト上で結合し、改行込みの原文範囲を電話番号候補として登録すること
- `株式会社`、`有限会社`、`合同会社`等の会社種別接頭辞に続く最大3行の組織名に単一改行が入った場合は、検出用テキスト上で結合し、NERが候補を返さない場合も形式検出の`ORGANIZATION`候補として登録すること。候補は改行込みの原文範囲を1件として表示し、接頭辞・組織指標のない一般文、空行、Markdown見出し、コードフェンスは結合しないこと。候補直後の`です`、`など`等の一般的な文脈語や、次行の`営業企画部`等の部署名は組織名へ含めないこと
- 2文字の漢字だけのNER候補が長い日本語複合語内にしか存在しない場合は除外すること
- `LOC`または`INS`として返された一般姓は、明示的な住所ラベル直後にある場合を除き、住所候補にしないこと
- モデルの最大長を超える原文はWorker内で分割し、320文字を上限、64文字を重複させること
- 分割位置は上限付近の句点・改行を優先し、重複領域の同一文字列候補は1件へ統合すること
- チャンク内の候補位置は原文全体の位置へ補正すること
- 採用モデルは評価結果に基づいて確定すること

### FR-05 候補の統合

- 同じ文字列の候補は、原則として文字列単位で1項目へ統合すること
- 検出元として、正規表現、NER、手動追加を識別できること
- 同一文字列が複数方式で検出された場合、検出元情報を失わないこと
- 原文中の出現数を表示すること

### FR-06 候補の確認・無効化・削除

各候補に対して以下を操作できること。

- 有効・無効状態を確認する
- 不要な対象を無効化してマスク対象から外す
- 候補一覧から削除する
- 原文中の該当箇所を確認する

自動検出候補は検出直後から有効なマスク対象とし、ユーザーが後から個別に無効化できること。再検出時は、ユーザーが無効化した既存項目を自動的に有効へ戻さないこと。
カテゴリは自動検出時または手動追加時に決定し、登録後は変更しない。カテゴリ変更は、永続保存または出力機能と合わせて将来検討する。

### FR-06a 原文上の候補確認

- 原文タブで、検出済み候補および手動追加済み対象の出現箇所を背景色で識別できること
- ハイライトは原文編集、文字列選択、手動追加を妨げないこと
- 原文の文字列とハイライトは同じ編集面で描画し、折り返しや最下部へのスクロールで位置がずれないこと
- 有効、無効、選択中の状態を視覚的に区別できること
- ハイライトは確認補助であり、マスク結果は引き続き原文と有効なマスク対象から生成すること
- マスク対象カードのアイコン操作で、原文タブでは原文、マスク結果タブでは対応するマスクトークンの最初の出現箇所へスクロールできること
- 原文のマスク対象ハイライトをクリックした場合も、対応するマスク対象カードを選択し、一覧内へスクロールできること
- マスク結果に対応トークンがない無効項目は原文タブへ切り替えて確認でき、現在の原文に存在しない項目の移動操作は無効であること

### FR-07 手動追加

- ユーザーが原文中の任意の文字列を選択して、マスク対象へ追加できること
- 手動追加時にカテゴリを指定できること
- 空文字、空白だけの文字列は登録できないこと
- 既に同一文字列が登録済みの場合は、重複登録せず既存項目へ誘導すること
- 1か所を選択しても、原文中の同一文字列すべてを対象とすることを明示すること

### FR-08 同一文字列の扱い

- 原則として同一文字列は原文中の全出現箇所を一括してマスクすること
- 手動追加、明確な構造化PII、明確な姓名候補は全出現箇所を対象とすること
- 自動検出された曖昧な一文字姓は、文脈付き出現箇所マスクで一般語パターンに一致した出現箇所を除外すること
- 文脈付き判定は自動検出の曖昧姓に限定し、任意の出現箇所をユーザーが個別編集する機能とはしないこと
- マスク対象から外した場合は、該当するマスク方式の全出現箇所へ反映すること
- 一致判定はMVPでは文字列の完全一致を基本とすること

### FR-08a 文脈付き出現箇所マスク

- 出現箇所マスクは`文脈付き（曖昧姓のみ）`を固定方式とし、管理パネルにモード切替UIを表示しないこと
- 設定はブラウザ保存せず、セッション消去後も固定方式を継続すること
- 文脈付きモードでは、`森`、`原`、`関`等の曖昧な一文字姓に限って出現箇所ごとの判定を行うこと
- `森林`、`原材料`、`関係`、`南側`、`東海`、`森の中`等の明らかな一般語パターンは、専用辞書に登録して除外すること
- 敬称、人名ラベル、姓名の連続、名簿・箇条書き、NERの人名結果がある場合は一般語パターンより人名判定を優先すること
- 人名・一般語のいずれとも断定できない場合は、検出漏れ防止のためマスクすること
- 候補カードでは、文脈付きモードでマスクされた出現数と検出総数を区別して確認できること
- マスク結果、原文ハイライト、最長一致の処理は、文脈判定後のマスク対象出現箇所と一致すること

初期の正規化ルールは以下とする。

- Unicodeは入力時にNFCへ正規化する
- 大文字・小文字は区別する
- 全角・半角は区別する
- 空白の有無は区別する

検出専用の正規化はマスク対象の一致規則を変更しない。`@`前後の半角・全角空白を除去したメール検出では、正規化後の検出範囲を原文へ戻し、空白を含む原文文字列を独立したマスク対象として登録する。原文、候補統合、マスク生成に正規化後テキストを使用してはならない。

### FR-09 包含関係と最長一致

- `山田`と`山田太郎`のような包含関係にある文字列を、それぞれ独立したマスク対象として登録できること
- 同じ開始位置で複数の対象が一致する場合、最長の文字列を優先すること
- 長い文字列として処理した範囲に、短い文字列のマスクを重複適用しないこと
- 長い文字列に含まれない短い文字列の出現箇所は、通常どおりマスクすること

例：

```text
登録対象:
山田      -> [PERSON_1]
山田太郎  -> [PERSON_2]

原文:
山田さんと山田太郎さん

結果:
[PERSON_1]さんと[PERSON_2]さん
```

### FR-10 マスクトークンの生成

- 同一の元文字列には、セッション内で同一のトークンを割り当てること
- 異なる元文字列には異なるトークンを割り当てること
- トークンからカテゴリを判別できること
- 原文中の既存文字列と衝突しにくい形式とすること
- 外部生成AIが分割・改変しにくい形式を評価して決定すること

表示候補：

```text
[[MASK_PERSON_A7F31C]]
[[MASK_ADDRESS_19B204]]
```

ユーザー向けの表示名として、`[人名_1]`などを併記してもよい。

### FR-11 マスク結果の生成

- マスク結果は、原文と現在有効なマスク対象一覧から都度生成すること
- 既存のマスク結果へ追加置換する方式を採用しないこと
- マスク対象の追加、無効化、削除後に再生成すること
- マスク結果は読み取り専用とすること
- 原文を内部的な基準データとして保持すること

### FR-12 原文・マスク結果の表示切り替え

- 「原文」と「マスク結果」を切り替えて表示できること
- 表示切り替えによってデータや設定を変更しないこと
- 原文表示は編集可能であること
- 原文上のマスク対象箇所をハイライトできること
- マスク結果上のトークンをハイライトできること
- 該当項目の選択時に、対応箇所を確認できること

この機能は原文の復元ではなく、マスク漏れと誤検出を確認するプレビュー機能とする。

### FR-13 原文編集後の再評価

- 原文変更後、登録済みマスク対象の出現数を再計算すること
- 出現数が0になった対象は自動削除せず、出現数0の対象として一覧へ残すこと
- 出現数0の対象を個別または一括削除できること
- 再び同じ文字列が入力された場合は、登録済み設定を適用すること
- AI・正規表現の再スキャンは、ユーザーが明示的に実行する方式を基本とすること

### FR-14 マスク結果のコピー

- マスク済みテキストをクリップボードへコピーできること
- コピー完了をユーザーへ通知すること
- 対象文字列数と置換箇所数を表示できること
- 主要なコピー操作はマスク結果画面に配置すること
- 原文を誤ってコピーする導線を避けること

### FR-15 マスクを含む文章の入力

- ユーザーがマスクを含む文章を貼り付けられること
- マスクを含む文章は原文とは別の状態として保持すること
- 入力欄へ原文やマスク結果を自動挿入しないこと

### FR-16 マスクの復元

- マスクを含む文章内に存在する既知のマスクトークンを対応する復元文字列へ置換できること
- マスクを復元した文章は読み取り専用とすること
- マスクを復元した文章をコピーできること
- 同じトークンが複数回存在する場合はすべて復元すること
- AIが削除・改変・分割したトークンは自動復元できないことを明示すること

### FR-17 トークン検証

マスクを含む文章に対して以下を検査できること。

- 文章内で確認できた既知トークン
- 文章内で確認できなかった既知トークン
- 対応表に存在しない不明トークン
- 既知トークンの出現回数

文章内容によって未使用トークンがあるため、「送信時の全トークンが文章内にも存在すること」を正常条件とはしない。

### FR-17a 同一人物の明示的な関連付け

- 新規の関連付けでは、マスク対象カードから2件以上の`PERSON`項目を選択し、同一人物として関連付けられること
- 既存の関連付けへの追加では、未関連付けの有効な`PERSON`項目を1件以上選択し、追加先の関連付けを指定できること
- 関連付けはユーザーが明示的に実行し、自動検出だけでは行わないこと
- 関連付けた項目は、各項目の`originalText`、原文上の出現箇所、出現数、検出元を保持すること
- 関連付けた項目へ同一の`relatedGroupId`とマスクトークンを設定すること
- 関連付け後のマスク結果では、選択した異なる表記を同じマスクトークンへ置換すること
- 新規の関連付け時に復元時の代表表記を候補表示し、ユーザーが修正できること
- 既存の関連付けへの追加時は、既存グループを選択肢から選び、そのグループのマスクトークンと復元文字列を引き継ぐこと
- 関連付けた項目の復元文字列は代表表記へ統一し、原文上の姓・姓名等の表記差は復元時に保持しないこと
- 有効状態でない項目、`PERSON`以外の項目、復元入力中のセッションは関連付け対象にできないこと
- 関連付け解除では原文表記ごとの項目を維持し、関連付けだけを解除できること
- 3件以上の項目が同一の関連付けに属する場合、解除時に「このマスクのみ解除する」または「同一の関連付けをすべて解除する」を選択できること
- 2件以下の関連付けの解除は、既存の動作を維持すること

### FR-18 現在の作業の消去

- 「現在の作業を消去」操作を提供すること
- 原文、候補、マスク対象、対応表、マスクを含む文章、マスクを復元した文章を初期化すること
- 誤操作防止の確認を表示すること
- JavaScript上の参照を破棄すること
- JavaScript実行環境のメモリを物理的にゼロクリアできるとは保証しないこと
- OPFSに保存済みのマスク対応表は削除しないこと

### FR-18A マスク対応表のローカル保存

- 明示操作なしでは原文、検出値、マスク対応情報を永続保存しないこと
- 明示保存時だけ、再適用・復元に必要な有効マスク対応表を暗号化してOPFSへ保存すること
- `originalText`、`maskedText`、`externalResponse`、`restoredResponse`、位置、選択範囲、一時UI状態を保存しないこと
- 「マスク対応表を保存」「保存済みの対応表を開く」「対応表を削除」「保存済みの対応表を全削除」を提供すること
- 対応表を開いたとき、原文を復元せず、現在の原文へ対応を再検索して適用すること
- 対応表のマスク方式が現在利用できない場合は部分適用せず拒否すること
- 一対一の対象・トークン対応を検証し、違反時は保存・読み込みを中止すること
- OPFS非対応時も一時利用のマスキング機能を継続できること
- 詳細は[マスク対応表のローカル保存要件](local-work-history-requirements.md)を正本とすること

### FR-19 ページ離脱時の注意

- 原文を含む作業は、明示保存の有無にかかわらずページ離脱や再読み込み後に再開できないことを表示すること
- 対応表の未保存変更がある状態でページを離れる場合、対応ブラウザの範囲で確認を出すこと
- ブラウザ標準の離脱確認文言をアプリが完全には制御できないことを前提とすること

## 10. データ保持要件

### 10.1 セッション中に保持するデータ

- 原文
- 自動検出候補
- マスク対象一覧
- トークン対応表
- マスクを含む文章
- マスクを復元した文章
- UI表示状態

### 10.2 既定で永続保存しないデータ

以下をLocalStorage、SessionStorage、IndexedDB、Cookie、サーバーへ保存しない。

- 原文
- 検出文字列
- マスク対象一覧
- トークン対応表
- マスクを含む文章
- マスクを復元した文章

上記の機密データのうち、再利用に必要な有効なマスク対応だけは、ユーザーが明示的に保存を確定した場合に限り、暗号化対応表としてOPFSへ保存できる。原文、処理結果、出現位置、無効候補は保存しない。OPFSの平文インデックスには、許可された一覧メタデータだけを保存する。

### 10.3 キャッシュを許容するデータ

- JavaScript、CSS、フォントなどの公開アプリ資材
- 同一オリジンで配信するONNX Runtime WASM/MJS
- NERモデルファイル
- トークナイザー設定・語彙ファイル

個人情報を含むセッションデータと、公開資材のブラウザキャッシュを区別する。

OPFS保存の詳細な暗号仕様、インデックス項目、障害復旧、競合制御、未保存変更判定は[マスク対応表のローカル保存要件](local-work-history-requirements.md)および[Storage API利用方針](storage-api-policy.md)で定義する。

## 11. 非機能要件

### NFR-01 プライバシー

- ユーザー入力をアプリケーションサーバーへ送信しないこと
- 入力内容をアクセス解析へ渡さないこと
- 入力内容をエラー監視サービスへ渡さないこと
- 入力内容をコンソールログへ出力しないこと
- 外部生成AI APIをアプリから直接呼び出さないこと
- 合成した固有マーカーを用いて、ネットワークリクエスト、Storage、Cookie、Cache名、Consoleへユーザー入力が混入しないことを自動検査すること

### NFR-02 セキュリティ

- 外部依存資材を最小化すること
- 使用するライブラリとモデルの配信元、バージョン、ライセンスを管理すること
- Content Security Policyを適用し、同一オリジンと公開NERモデル配信元以外への接続を許可しないこと
- 本番ホストではCSP、フレーム埋め込み拒否、MIMEスニッフィング拒否、Referrer Policy、Permissions PolicyをHTTPヘッダーで適用すること
- ユーザー入力をHTMLとして直接描画しないこと
- XSS対策を実施すること
- 本アプリが「完全な安全」や「匿名化」を保証する表現を使用しないこと

推奨説明：

> 入力したテキストとマスク対応表は、外部サーバーへ送信せず、現在のブラウザ内で処理します。

### NFR-03 性能

PoCで以下を測定し、MVPの受入基準を確定する。

- モデル初回ダウンロード時間
- モデル初期化時間
- 1,000文字、10,000文字および30,000文字の検出時間
- 最大メモリ使用量
- WebGPUとWASMの差
- ChromeとEdgeの差
- 長文分割時の境界検出漏れ

形式検出とマスク生成は、合成した1,000文字、10,000文字および30,000文字で中央値を継続計測する。回帰防止上限は、1,000文字で形式検出500ms・マスク生成100ms、10,000文字で形式検出3,000ms・マスク生成500msとする。30,000文字の回帰防止上限は、実機ベースライン取得後に追加する。この上限は端末差を吸収する重大回帰検出値であり、通常性能の目標値ではない。

処理中は進行状態を表示し、ユーザーが同じ操作ボタンから停止できること。NER処理は開始から5分でタイムアウトし、停止またはタイムアウト後に再実行できること。

### NFR-04 可用性・エラー処理

- モデル取得失敗時に再試行できること
- モデル取得、初期化、推論の失敗、タイムアウト、中止後の再試行では、失敗したWorkerと初期化状態を再利用せず再生成すること
- モデルが利用できない場合でも、手動追加と正規表現検出を利用できる設計を目標とすること
- エラー発生時に原文と既存のマスク設定を失わないこと
- 手動中止時は取得済みの形式候補を反映し、原文変更または現在の作業の消去による中止時は遅延した検出結果を反映しないこと
- エラー内容に原文や検出文字列を含めないこと

### NFR-05 操作性

- コピー前にマスク結果を確認しやすいこと
- 自動検出結果と手動追加を識別できること
- 出現数と、カテゴリを含む表示トークンを一覧で確認できること。表示トークンと重複する独立したカテゴリ表示は設けないこと
- マスク対象の追加・無効化・削除結果が即時にプレビューへ反映されること
- モデルの初回取得が必要な場合、容量と進行状況を表示すること

### NFR-06 アクセシビリティ

- マウスだけでなくキーボードでも主要操作ができること
- 色だけに依存せず、ラベルやアイコンでも状態を表現すること
- フォーカス位置を視認できること
- 原文とマスク結果の切り替えを支援技術から識別できること

## 12. 初期データモデル

```ts
import type { DetectionNormalizationRule } from "./normalization/detection/types";

type MaskCategory =
  | "PERSON"
  | "ADDRESS"
  | "ORGANIZATION"
  | "PHONE"
  | "EMAIL"
  | "POSTAL_CODE"
  | "SECRET"
  | "OTHER";

type DetectionSource = "regex" | "ner" | "manual";

type OccurrenceMaskingMode =
  | "global"
  | "contextual_ambiguous_surnames";

type MaskEntry = {
  id: string;
  originalText: string;
  restorationText: string;
  token: string;
  relatedGroupId?: string;
  category: MaskCategory;
  sources: DetectionSource[];
  confidence?: number;
  normalizationRules?: DetectionNormalizationRule[];
  enabled: boolean;
  occurrenceCount: number;
};

type MaskSession = {
  originalText: string;
  entries: MaskEntry[];
  externalResponse: string;
  occurrenceMaskingMode: OccurrenceMaskingMode;
};
```

`maskedText`と`restoredResponse`は保存の正本とせず、セッション状態から生成する派生データとする。`restorationText`は検出時または手動追加時に確定する項目データとし、復元時に`normalizationRules`から再計算しない。検出補正がない場合は`originalText`と同一にする。

## 13. 受入条件

### AC-01 同一文字列の一括マスク

原文内に同じ文字列が複数存在するとき、一括モードまたは手動追加・明確な候補では、対象を有効化すると全出現箇所が同じトークンへ置換されること。文脈付きモードの曖昧な一文字姓だけは一般語パターンに一致した箇所を除外する。

### AC-02 任意の出現箇所を個別指定しない

同一文字列の任意の出現箇所をユーザーが個別に有効または無効にする操作は存在しないこと。ただし、文脈付きモードでは自動検出された曖昧な一文字姓について、一般語パターンに一致した出現箇所を自動的に除外できること。

### AC-03 最長一致

`山田`と`山田太郎`を登録した状態で、`山田太郎`が短いトークンと`太郎`へ分断されず、長い対象のトークンへ置換されること。

### AC-04 原文基準の再生成

マスク対象を追加、削除、無効化した後も、マスク結果が原文から再生成され、置換の重複や崩れが発生しないこと。

### AC-04-1 検出補正候補の復元

検出用正規化が適用されたマスク対象は、候補表示とマスク結果では補正前の原文範囲全体が一つのトークンへ置換され、復元時には検出が成立した補正後文字列へ置換されること。全角ASCII、ハイフン種類、メールの`@`周辺空白、日本語文字間空白、構造化PII・氏名・組織の内部改行、および行末ハイフン継続が、検出時と同じ結果へ補正されること。補正のない候補と手動追加候補は原文表記へ復元されること。外部文章内でトークンが原文と異なる位置へ移動していても結果が変わらず、復元時に周辺文脈から補正を推測しないこと。

### AC-05 表示切り替え

原文とマスク結果を切り替えても、原文、候補、マスク対象が変更されないこと。

### AC-06 コピー

コピーされる内容が表示中のマスク結果と一致し、原文が意図せずコピーされないこと。

### AC-07 マスクの復元

マスクを含む文章に既知トークンが含まれる場合、対応する元の文字列へすべて置換できること。

### AC-07a 同一人物の関連付け

新規の関連付けでは有効な`PERSON`カードを2件以上選択し、既存の関連付けへの追加では1件以上選択して関連付け方法と追加先を確定した場合、原文上の各表記が同じマスクトークンへ置換されること。関連付けた対象を復元すると、新規作成時に確定した代表表記または追加先グループの代表表記へ置換されること。関連付け前の`originalText`と出現数は保持されること。

### AC-07b 同一人物の関連付け解除

3件以上の項目が同一の関連付けに属する場合、カードの操作メニューから解除方法を選択できること。「このマスクのみ解除する」では選択した項目だけが個別のマスクへ戻り、残りの項目は関連付けを維持すること。「同一の関連付けをすべて解除する」ではグループ内の全項目が個別のマスクへ戻ること。いずれの場合も各項目の原文表記、元のトークン、復元表記が復元されること。

### AC-08 不明・欠落トークンの検査

マスクを含む文章内の既知、不明、未出現トークンの状態を区別して表示できること。

### AC-09 セッション破棄

保存操作を行わずにページを再読み込みした場合、原文、候補、マスク対象、マスクを含む文章、マスクを復元した文章が復元されないこと。保存済み対応表は一覧から別途開けるが、原文や作業画面は復元されないこと。

### AC-09A マスク対応表の保存と再適用

明示保存した対応表をブラウザ再起動後に開くと、対応表名の確認、パスフレーズの検証、対象・トークン・復元文字列・種別・検出元・マスク方式の読み込みができること。現在の原文がある場合だけ対応を再検索してマスク結果を生成し、原文、外部回答、復元結果、復元セクションを復元しないこと。

### AC-09B インデックスの平文境界

`index.json`にランダムID、対応表名、作成・更新日時、暗号化ファイル名、フォーマットバージョン、リビジョン以外の情報が含まれないこと。原文、抜粋、検出値、トークン対応、マスク内容、カテゴリ具体値、件数、プレビューが含まれないこと。

### AC-10 ネットワーク送信

ブラウザの開発者ツールで確認したとき、原文、検出文字列、対応表、マスクを含む文章がネットワークリクエストへ含まれないこと。

### AC-11 Phase 2：形式検出候補

メールアドレス、電話番号、郵便番号を含む原文で自動検出を実行すると、各対象が`EMAIL`、`PHONE`、`POSTAL_CODE`の有効なマスク対象として管理パネルへ表示され、検出元が形式検出として識別できること。

### AC-12 Phase 2：自動検出対象の無効化

形式検出直後から同一文字列の全出現箇所が対応するトークンへ置換されること。ユーザーが`無効化`すると原文表記へ戻り、再度`有効化`できること。

### AC-13 Phase 2：再検出と統合

自動検出を複数回実行しても同じ文字列の候補が重複せず、既存項目と一致した場合は検出元情報が追加され、手動で設定済みのカテゴリ、有効・無効状態、トークンが維持されること。無効化済みの対象を再検出しても自動的に有効へ戻らないこと。

### AC-14 Phase 3：ローカルNER候補

人名、地名、組織名を含む日本語原文で自動検出を実行すると、NER由来の候補が有効なマスク対象として管理パネルへ表示され、検出元`AI検出`と信頼度が確認できること。NER候補は検出直後からマスク結果へ反映され、不要な対象は個別に無効化できること。

### AC-15 Phase 3：NER障害時の継続

NERモデルの取得、初期化、推論に失敗またはタイムアウトした場合でも、形式検出で得られた候補は管理パネルへ表示され、原文、既存候補、手動追加済みマスク対象が失われないこと。エラー表示には原文や候補文字列を含めないこと。次の`再検出`では新しいWorkerでモデル初期化から再試行できること。処理中の`中止`では形式候補を反映し、原文変更または現在の作業の消去後に完了した古い処理結果は画面へ反映しないこと。

### AC-16 Phase 3：人名補助検出

`氏名佐藤健一`、`品質管理担当の佐藤健一`、`顧客である田中美咲`、`合同会社みらいテクノロジーの鈴木一郎`、`氏名Taro Yamada`、`名義人TARO YAMADA`のような文脈付きの姓名は、NERが返さない場合でも人名候補として表示できること。Markdown表・CSVの人名列、キー値行、妥当なJSONの既知人名フィールドにある日本語・英語氏名も検出できること。一方、文脈のない`Taro Yamada`は形式検出せず、NERが`PER`として返した場合だけ人名候補として表示すること。検出済みの`高橋健太`と独立した`高橋`が共存する場合は、`高橋`を初期有効の人名候補として表示し、一括モードでは`高橋駅`など同じ文字列を含む複合語内も同じトークンでマスクすること。文脈付きモードでは、そのような複合語を一般語パターン辞書に登録した場合に限り該当箇所を除外する。さらにMarkdownの単一値コードブロックに`高橋由美`がある場合は、別の人名候補として表示できること。

### AC-17 Phase 5：ハードニング

本番ビルドへCSPメタタグが含まれ、配信時にセキュリティヘッダーを適用できること。ChromiumとMicrosoft Edgeで、初期表示、NER障害時の形式候補継続、入力データ非送信、WCAG 2 A / AAの自動検査が成功すること。形式検出とマスク生成の1,000文字・10,000文字計測が回帰防止上限内であり、現行入力上限である30,000文字も性能確認対象として扱うこと。

### AC-18 Phase 6：OCR崩れメール・URL

全角ASCII互換文字を含むメール・URLと、メールの`@`・`.`、URLの安全な構造記号、メール・URLの行末ハイフン周辺で複数回単一改行した文字列を、原文表記のまま有効な候補として表示できること。行末ハイフンは保持し、通常文の改行、URL直後の次行、空行、Markdown区切りを誤って結合しないこと。正規化後のテキストを原文として保存せず、候補範囲は全角記号・空白・改行を含む原文上の連続範囲へ戻すこと。

### AC-18a Phase 6：OCR崩れ電話番号

`090-1234-\n5678`、`052-\n123-4567`、`080-9876-\n5432`のように電話番号の数字・ハイフン間へ単一改行が入った表記は、改行を除去した検出用テキストで電話番号として検出し、改行込みの原文範囲を1件の`PHONE`候補として表示できること。同じ範囲内の`123-4567`などを`POSTAL_CODE`候補として重複表示・マスクしないこと。通常文の改行は結合しないこと。

### AC-18b Phase 6：OCR崩れ組織名

`株式会社\n青葉デジタル\nソリューションズ`のように会社種別接頭辞に続く組織名が最大3行に分かれた場合、検出用テキストでは組織名全体を連結し、NERが候補を返さない場合も形式検出の`ORGANIZATION`候補として表示できること。候補は改行込みの原文範囲を1件として表示し、`ーションズ`など長い候補に包含される断片は表示しないこと。候補直後の`です`、`など`等の一般的な文脈語や、次行の`営業企画部`等の部署名は組織名へ含めないこと。接頭辞・組織指標のない一般文、空行、Markdown見出し、コードフェンスは結合しないこと。

### AC-19 Phase 6：OCR崩れ姓名

`山田\n太郎`のように姓名間へ単一改行が入った表記、`山 田 太 郎`や`佐　藤　健　一`の完全分割表記、`山 田　太郎`や`山　田太　郎`の混在表記は、限定条件を満たす場合に空白・改行なしの姓名として検出できること。一般姓で始まる漢字姓名の文字間スペース表記はNERの成否に依存せず形式候補として登録し、候補を原文表記へ戻せること。一覧行、箇条書き、Markdown表セルの`鈴木一郎すずきいちろう`のような連結表記では、漢字姓名だけを候補化し、読み仮名内の組織・住所NER断片を表示しないこと。同じ正規化文字列になる表記が複数あっても、原文位置ごとに候補を保持してから原文表記へ戻すこと。通常文、句読点・空行を挟む表記、4文字以上の行末・行頭漢字列、連続空白、タブ、前後が日本語文字に直結する部分範囲、Markdown見出し・コードブロック内の姓名間改行を誤結合しないこと。

### AC-20 Phase 6：OCR崩れ住所と補正表示

都道府県、市区町村、町域、丁目・番地・号等の構成要素の境界で複数行に折り返された住所を、改行込みの原文表記で1件の有効な候補として表示できること。包含される未補正の短い住所候補は重複表示しないこと。空行、通常文、Markdown見出し・コードフェンスをまたいで住所を生成しないこと。正規化を経た候補カードには、住所改行、メール・URL改行、行末ハイフン等の補正内容を日本語で表示すること。

姓辞書に一致する姓と1〜4文字の漢字名が連続した原文範囲は、空白・句読点・文書境界などの明確な区切りがある場合に形式候補として検出する。曖昧姓も姓名全体なら検出対象に含め、番号付き・箇条書きの名簿やMarkdown表・CSV・キー値行での検出漏れを抑える。`姓`・`名字`・`苗字`ラベルの値が辞書姓だけの場合も、PERSONの単独姓候補として登録する。一覧項目の境界を越える一般語・組織名は候補化せず、明らかな組織・地名接尾辞は除外する。今回の姓辞書強化では適合率より再現率を優先し、人名である可能性が一定以上ある候補をユーザー確認対象に含める。
