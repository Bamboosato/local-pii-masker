# マスク対応表のローカル保存要件（MVP）

## 1. 目的と正本表現

デフォルトではユーザーデータを永続保存しない。ユーザーが明示的に保存操作を行った場合に限り、マスク対象文字列とマスク文字列の対応関係を暗号化してOPFSへ保存する。外部サーバーおよびクラウドへの送信・保存は行わない。

原文を含む作業セッションは保存・復元しない。本機能は、新しく入力した原文へ過去のマスク対応を再適用したり、新しく貼り付けたマスク済み文章を復元したりするための対応表を扱う。

画面・文書では次の説明を使用する。

> 原文、検出値、マスク対応情報などの機密データは暗号化されます。対応表一覧に表示する対応表名、保存日時は暗号化されません。

対応表名の入力欄には次を表示する。

> 対応表名は暗号化されません。氏名、住所などの個人情報を入力しないでください。

## 2. 保存対象

暗号化本文へ保存するのは、再適用と復元に必要な次の対応表データだけとする。

- `schemaVersion`
- ランダムな対応表ID、対応表名、作成日時、更新日時、リビジョン
- マスク方式
- 有効なマスク対応エントリ
- エントリの安定ID
- マスク対象文字列と正規化済み対象文字列
- 対応するマスク文字列（トークン）と復元文字列
- マスク種別、検出元、手動追加・編集フラグ
- 関連付けを再現するための安定した関連ID（使用時のみ）

無効化された候補は、MVPでは保存しない。無効化は現在のインメモリ作業における再検出時の判断として扱う。無効項目を含む完全な編集履歴が必要になった場合は別要件とする。

## 3. 保存しないデータ

次はOPFS、LocalStorage、SessionStorage、IndexedDB、Cookie、Cache Storage、Service Worker、URL、ログ、分析、エラー報告へ保存または出力しない。

- `originalText`
- `maskedText`
- `externalResponse`
- `restoredResponse`
- 原文の抜粋、文脈、出現位置、選択範囲
- 一時的な検出候補、無効候補、通知、ダイアログ、タブ、開閉状態
- 鍵、パスフレーズ

保存済み対応表を開いても、原文・処理結果・復元セクションは復元しない。現在の原文があれば対応表を再適用してマスク結果を既存ロジックで生成する。

## 4. 対応表の再適用

- 原文を保存せず、読み込んだ対応表の文字列を現在の原文から再検索する。
- 既定は正規化後の完全一致とする。
- 同じ対象文字列の全出現箇所に同じトークンを適用する。
- 重なりは最長一致を優先し、同じ長さは正規化文字列、トークン、安定IDの順で決定する。
- 新たに検出・手動追加する候補のトークンは、読み込んだ対応表と現在の原文に対して衝突しないものを生成する。
- 対応表のマスク方式が現行実装で利用できない場合、部分適用せず読み込みを拒否する。
- 自動適用後の候補は画面で確認・無効化・編集できる。出現位置は保存せず、現在の原文から再計算する。

対応表の永続化では、1つの対象文字列に複数トークン、または1つのトークンに複数対象文字列となるデータを拒否する。現在の画面が持つ同一人物関連付けなど、既存のインメモリ機能を壊さないため、対応表への保存時に一意性違反を通知して保存を中止する。

## 5. 復元

- 既知トークンは完全一致で全出現箇所を対応する復元文字列へ置換する。
- 不明トークンは変更せず、既知・未出現・不明を別々に表示する。
- 対象・トークンの重複、部分一致、重なり、形式不正は対応表の読み込み時に拒否する。
- トークンに見える文字列が外部回答へ自然に入力された可能性は自動判定できないため、既知トークンの置換結果を利用者が確認できる注意を表示する。
- 原文の意味を推測して、削除・改変されたトークンを復元しない。

## 6. 平文インデックス

`local-pii-masker/index.json` は一覧表示と競合検出のため平文とする。各項目に保持できるのは次に限定する。

- ランダムな対応表ID
- ユーザー指定の対応表名
- 作成日時・更新日時
- 暗号化ファイル名
- 暗号化フォーマットのバージョン
- 競合検出用リビジョン

原文、抜粋、検出値、トークン対応、マスク内容、カテゴリの具体的な値、件数、プレビューは含めない。ファイル名・ディレクトリ名にもユーザー入力を使用しない。

## 7. 暗号仕様

- 暗号化：AES-GCM、鍵長256bit、タグ長128bit
- 鍵導出：PBKDF2、SHA-256
- Salt：保存処理ごとに暗号学的乱数で16byte
- IV：暗号化ごとに暗号学的乱数で12byte
- パスフレーズ：NFKC正規化後12文字以上
- 圧縮：gzip
- 処理順：JSON → UTF-8 → gzip → AES-GCM
- 鍵とパスフレーズ：永続保存しない。処理完了後に参照を保持しない
- 上書き保存：パスフレーズを再入力する

Envelopeヘッダーには`format`、`formatVersion`、KDF名、ハッシュ方式、反復回数、Salt、暗号方式、鍵長、IV、タグ長、圧縮方式、暗号本文を保持する。`format`、`formatVersion`、暗号・KDF・圧縮パラメータは決定的にシリアライズしてAES-GCMのAADへ指定し、ヘッダー改ざんを認証エラーとして検出する。

PBKDF2の反復回数は対象端末で鍵導出が概ね250～500msになるよう保存時に測定・調整し、Envelopeへ保存する。実装の最低許容値は100,000回、上限は2,000,000回とし、範囲外のEnvelopeは拒否する。測定値はログへ出力しない。

## 8. OPFS構成と障害復旧

```text
local-pii-masker/
├─ index.json
├─ index.backup.json
├─ mappings/
│  └─ {mapping-id}.mapping.enc
└─ temporary/
   ├─ {mapping-id}.tmp
   └─ index.tmp
```

保存は一時ファイルへ書き込み、読み戻し・復号検証してから正式ファイルとインデックスを更新する。OPFSが完全な原子的置換を保証すると仮定せず、既存の正常な暗号化ファイルとインデックスをバックアップ・ロールバックで維持する。

- `index.json`破損：`index.backup.json`から復旧を試みる
- インデックスのみ存在：保存データ欠損として表示し、削除可能にする
- 暗号化ファイルのみ存在：孤立ファイルとして保持し、自動削除しない
- 一時ファイルのみ存在：未完了処理として安全性を確認し、削除候補にする
- 暗号化ファイル破損・改ざん・パスフレーズ不一致：一覧情報を残し、「データを開けません」と表示する
- インデックス更新失敗：新規暗号化ファイルを孤立状態にしないよう可能な範囲でロールバックする

暗号化ファイルだけから対応表名を復元できないため、インデックスの完全な自動再構築は保証しない。

## 9. 未保存変更と複数タブ

未保存変更は、保存または読み込み完了時の永続化対象（有効な対応表エントリとマスク方式）を安定した順序でシリアライズしたフィンガープリントと現在値を比較して判定する。原文、`maskedText`、外部回答、復元結果、一時UI状態は対象外とする。

同じ対応表への同時更新は正式サポートしないが、破損防止のため次を行う。

- Web Locks APIが利用可能なら保存・削除・インデックス更新を排他制御する
- 利用できなければリビジョンによる楽観的競合検出を行う
- 読み込み時と保存直前でリビジョンが異なる場合は上書きしない
- 競合時は再読み込みまたは名前を付けて保存するよう案内する
- 閲覧・復元は複数タブで許可する

## 10. UIと非対応環境

操作名は「マスク対応表を保存」「保存済みの対応表を開く」「対応表を削除」「保存済みの対応表を全削除」とする。「作業を保存」「作業を復元」「履歴を開く」といった作業セッションを示す表現は使わない。

「現在の作業を消去」はインメモリの原文・候補・外部回答だけを初期化し、保存済み対応表を削除しない。「保存済みの対応表を全削除」はOPFS内の保存データを削除するが、画面上の作業を自動消去しない。両者の確認ダイアログを分離する。

OPFS非対応、容量不足、権限拒否の場合も、原文入力、検出、手動追加、マスキング、コピー、復元は一時利用できる。画面には対応表保存だけが利用できない理由と、原文が保存されないことを示す。

## 11. テスト観点と受入基準

### 機能観点

- 正常：保存・一覧・パスフレーズ付き読み込み・新しい原文への再適用・新しいマスク済み文章の復元
- 異常：誤パスフレーズ、改ざん、破損、未対応スキーマ、反復回数不足、対応の一意性違反
- 境界：12文字パスフレーズ、長短の重なり、同一対象の全出現、空の現在原文、不明トークン
- 状態遷移：保存前／保存済み／編集後／読み込み中／競合／削除後

### 非機能・データ・UI観点

- 暗号化ファイルに機密データの平文がなく、indexに許可外項目がない
- LocalStorage等、Cache Storage、Service Worker、ネットワーク、Console、エラー報告へユーザーデータが出ない
- OPFS非対応でも従来の一時利用が継続する
- Web Locks利用時と非対応時の競合が破損を生まない
- 保存失敗時に既存の正常データと画面上の作業を保持する
- 対応表UIが作業セッションの復元と誤認させず、削除操作が分離される
- キーボード操作、フォーカス復帰、エラー・空・読み込み状態を確認する
