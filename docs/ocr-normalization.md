# Phase 6 OCR崩れ対応

## 1. 目的

OCRやPDFテキスト抽出で生じる表記崩れを、原文を変更せずに検出用テキストだけで補正する。検出結果は位置対応マップを使って原文上の連続範囲へ戻し、マスクは原文表記へ適用する。

処理フローは以下とする。

```text
原文
↓
用途別の検出用正規化
↓
形式検出
↓
正規化範囲を原文範囲へ変換
↓
原文表記の候補として統合・マスク
```

## 2. 初期実装

### 2.1 対応ルール

| ルール | 内容 | 適用先 |
| --- | --- | --- |
| `fullwidth_ascii` | `！`～`～`の全角ASCII互換文字を半角化 | メール、URL |
| `hyphen_variants` | `−`、`ー`、`―`、`‐`、`–`、`—`等をASCIIハイフンへ統一 | メール、URL |
| `email_at_spacing` | メールの`@`前後にある半角・全角空白を除去 | メール |
| `email_line_break` | メールの`@`、`.`、行末ハイフン周辺にある複数の単一改行を除去 | メール |
| `url_line_break` | URLの`.`、`/`、`?`、`&`、`=`、`#`、行末ハイフン周辺にある複数の単一改行を除去 | URL |
| `line_end_hyphen` | 行末ハイフンを保持したまま直後の改行を除去 | メール、URL |
| `phone_line_break` | 電話番号の数字・ハイフン間にある単一改行を除去 | 電話番号 |
| `organization_line_break` | 会社種別・会社/法人/センター等の組織指標を含む組織名の途中にある単一改行を除去 | NER・形式検出 |
| `address_line_break` | 都道府県・市区町村・町域・丁目・番・号の境界にある単一改行を除去 | 住所 |
| `person_name_line_break` | 限定条件を満たす姓名間の単一改行を除去 | NER |
| `japanese_inter_character_space` | 完全分割表記と一般姓で始まる混在表記の単一空白を除去 | 形式検出、NER |

`fullwidth_ascii`と`hyphen_variants`は構造化PII検出用に限定する。NERへ無条件適用すると、カタカナの長音`ー`などを壊すため、NER入力全体へは適用しない。

候補の`originalText`は、全角記号、空白、改行を含む補正前の原文表記を保持する。同じ原文表記が複数回ある場合は、既存要件どおりすべて同じトークンでマスクする。検出補正が適用された候補は、検出が成立した正規化後の一致範囲を`restorationText`として保持し、復元時に使用する。候補表示、原文ハイライト、出現数計算、マスク範囲は引き続き`originalText`を使用する。補正のない候補と手動追加候補では`restorationText`を`originalText`と同じ値にする。

## 3. 誤結合防止

- 通常文の改行は削除しない。
- メール・URL改行は構造記号または行末ハイフンの隣に限定し、空行をまたがない。
- 行末ハイフンは文字列の一部として保持し、改行だけを除去する。
- 住所改行は都道府県・市区町村・町域・丁目・番・号が連続して完全な住所になる範囲だけを対象にする。
- Markdownの`---`をURLのハイフン継続として扱わない。
- Markdown見出し、表、コードフェンスを原文上で変更しない。
  - 姓名間改行は前行末・次行先頭が各1～3文字の漢字列で、前側が行頭または区切り文字に接する場合、または一般姓の後ろに名の一部が残る場合だけ除去する。
- 姓名間に句読点・空行がある場合や、Markdown見出し・コードブロック内では除去しない。
- 日本語文字間スペースは、3～7文字の漢字・カタカナが各文字間の単一空白で完全に分割された場合と、一般姓で始まり空白が2か所以上ある混在表記だけ除去する。一般姓で始まる漢字姓名は、NERが個別の出現位置を返さない場合に備えて形式候補としても直接登録する。
- 単語間空白1個、連続空白、タブ、改行、前後が漢字・カタカナへ連結する部分範囲は除去しない。
  - 同じ姓名へ正規化される複数の原文表記は、NER候補を位置ごとに保持して個別に原文範囲へ戻す。
  - NERが正規化後テキストの一部の出現位置だけを返した場合も、同じ候補文字列の全出現位置を原文範囲へ展開する。通常表記と改行表記はそれぞれの原文表記として候補登録する。
- 一覧行、箇条書き、Markdown表セルで、一般姓から始まる漢字姓名に4～12文字のひらがな読みが直接続く場合は、漢字姓名だけを候補化する。通常文中の連続文字列へは適用しない。
- `株式会社`、`有限会社`、`合同会社`等の会社種別、または`会社`、`法人`、`センター`、`ソリューションズ`等の組織指標を含む最大3行の組織名は、単一改行だけを検出用テキスト上で除去する。組織指標のない一般文、空行、Markdown見出し、コードフェンスでは結合しない。
- 上記の正規化イベントは、NERが候補を返さない場合も、原文範囲を保持した`ORGANIZATION`の形式候補として登録する。
- 組織候補の末尾にある`です`・`など`等の一般的な文脈語、または直後の`営業企画部`等の部署名は、組織名に含めず原文範囲から除外する。
- 氏名直後の読み仮名内で分割された組織・住所NER候補は、原文位置に基づいて除外する。独立したひらがな組織候補は一律に除外しない。
- 正規化後テキストを自動保存せず、明示保存時に原文の正本として暗号化OPFSへ保存する場合は[ローカル作業履歴 追加要件](local-work-history-requirements.md)に従う。

## 4. テスト観点

- 機能観点：全角メール・URL、複数位置で改行したメール・URL、行末ハイフン、住所折り返し、姓名間改行、各文字間空白を候補化できること
- 機能観点：全角メール・URL・電話番号、複数位置で改行したメール・URL・電話番号、行末ハイフン、住所折り返し、姓名間改行、各文字間空白を候補化できること
- 非機能観点：原文を変更せず、既存の30,000文字上限と性能予算を維持すること
- データ観点：半角・全角混在、LF・CRLF、複数区切り、同一文字列の複数出現を確認すること
- UI観点：候補カード、原文ハイライト、マスク結果が同じ原文範囲を示し、候補カードに適用した補正内容を日本語で表示すること
- 正常系：全角ASCII、ハイフン、空白、改行等を補正して検出したメール、URL、電話番号、住所、氏名、組織は、原文位置と異なる外部文章内でも検出時の補正後文字列へ復元できること
- 異常系：通常文の改行、URL直後の次行、Markdown区切りを結合しないこと
- 境界値：候補先頭・末尾、サロゲートペア前後、LF・CRLF・CR、連続空白、全角・半角混在、複数種類のハイフンを含む範囲を確認し、検出時に一致した範囲だけを補正後文字列へ反映すること
- 状態遷移：再検出でも候補を重複作成せず、有効・無効状態と確定済みの`restorationText`を維持すること。復元入力の編集や同一トークンの複数出現によって復元文字列が変化しないこと
- 競合：同じ原文表記に未補正候補と補正後候補、または異なる補正後候補が統合されても、定義した優先順位で`restorationText`を決定すること
- 回帰：補正のない自動候補と手動追加候補は原文表記のまま復元すること。テキスト正規化画面で原文へ適用済みの補正を復元時に重ねて適用しないこと
- 競合：電話番号内の郵便番号候補、構造化候補内のNER断片、組織・住所の入れ子候補を除外し、姓・姓名のPERSON候補は両方維持すること

## 5. 対象外

Phase 6で予定した住所折り返し、メール・URL・電話番号の複数行折り返しとハイフン継続、候補カードの補正ルール表示まで実装済みとする。以下は引き続き対象外とする。

- OCRエンジン、画像、PDFの読み込み
- `O/0`、`I/1`などOCR誤認識文字の自動訂正
- 縦書き1文字改行の完全対応
- LLMによる補正
