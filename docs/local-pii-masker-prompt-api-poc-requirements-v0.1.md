- バージョン：0.1（2026-10-27 実装前確認反映）
- 作成日：2026-10-27（日本時間）
- 対象：`Bamboosato/local-pii-masker`
- 対象リポジトリ：https://github.com/Bamboosato/local-pii-masker
- 位置付け：小規模PoCの追加要件と、ローカルCodexへの実装指示
- 状態：PoC機能実装・対象自動試験まで完了、実モデル評価待ち。精度・速度の改善は未検証。依存監査は後続の承認済み修正で解消（評価報告・docs/ci.md参照）

## 1. 目的と判断したいこと

デスクトップ版ChromeのPrompt API（Gemini Nano）を使い、既存の正規表現・補助ルール・日本語NERでは見落とす個人情報を、端末内で追加検出できるか検証する。

最優先は検出漏れの削減とする。同時に、誤マスク、利用者の確認負担、処理時間、利用端末の制約が許容できるかを評価する。単に候補件数が増えたことを精度改善とは扱わない。

PoCでは次の問いに答える。

1. 文脈を利用した追加検出により、人名・住所・組織名の見落としを減らせるか。
2. 追加された正しい候補に対し、誤候補と一括置換による誤マスクがどれだけ増えるか。
3. 現行NERに追加する運用が、実機の待ち時間・メモリ負荷・操作の面で成立するか。
4. 将来の検討材料として、既存NERをGemini Nanoへ置き換える方式にも価値があるか。

本PoCの完了と、本番機能としての採用は別判定とする。改善が確認できない場合も、再現可能な結果と不採用理由を残せばPoCは完了とする。

## 2. 前提と既存仕様の扱い

本書は、作成時点で確認したREADME、`docs/architecture.md`、`docs/model-evaluation.md`と会話上の合意に基づく。実装担当は作業開始時のローカルソースと既存文書を照合する。

| 項目 | 本PoCでの扱い |
| --- | --- |
| 既存検出 | 正規表現・補助ルール・ONNX NERを基準方式として維持する |
| 既存NER | `jiting/xlm-roberta-ner-japanese_onnx`を基準とする。最新ソースで異なる場合は記録する |
| マスク生成・復元 | 既存のマスクエンジン、トークン生成、復元対応表を使う |
| 入力の正本 | 現在エディターに確定している原文。明示適用済みの正規化結果は新しい原文として扱う |
| 入力上限 | 現行30,000文字（UTF-16コード単位）の範囲で検証する。上限を拡張しない |
| 同一文字列 | 原則全出現箇所を一括マスクする。曖昧な一文字姓に対する既存例外も維持する |
| ユーザーの選択 | 手動追加、無効化、関連付け等の既存状態を尊重する |
| 一時データ | 追加検出用の入力・応答・未確定候補はアプリのメモリ内だけで扱う |
| 対応表保存 | 明示操作による既存保存機能を維持し、PoC都合で形式変更しない |

過去の評価値を現在の基準値として流用せず、今回固定する同一コミット・同一データで基準方式を再測定する。

## 3. 対象範囲

### 3.1 必須の実装範囲

- 任意実行の「追加AI検出（試験）」機能。
- Prompt APIの利用可否判定、モデル準備・取得状況の表示。
- 日本語テキストからの人名・住所・組織名の候補抽出。
- JSON Schemaによる出力形式の制約と、アプリ側の入力照合・位置計算。
- 既存検出結果との差分表示、選択した追加候補の適用。
- 長文分割、進捗、中止、タイムアウト、原文変更時の結果破棄。
- 基準方式と追加方式を比較できるブラウザ評価手段。
- 回帰・異常系の確認と、合成データを使った実機評価報告。

### 3.2 検出対象と期待する効果

| カテゴリ | 評価する例 | 検出方針 |
| --- | --- | --- |
| `PERSON` | 未知の漢字氏名、ひらがな・カタカナ氏名、姓のみ、人名フィールドの値 | 周辺文、ラベル、敬称等を手掛かりに、実在する入力文字列を候補化する |
| `ADDRESS` | 文中の住所、既存NERが部分的にしか拾わない住所 | 明示された住所文字列を抽出する。省略部分を推測・補完しない |
| `ORGANIZATION` | 会社・団体・組織として言及された名称 | 名前の範囲を抽出する。施設の住所扱い等は既存評価定義に合わせる |

地名・施設名は、それだけで常に個人情報になるとは限らない。既存のマスキング対象方針に合わせて正解ラベルを定義し、PoCの途中で対象範囲を拡張しない。電話・メール・認証情報等の形式検出は既存ルールに任せ、本PoCのモデル抽出対象は上記3カテゴリに限定する。

### 3.3 対象外

- Gemini Nanoによる文章全体の書き換え、直接のマスキング、復元文生成。
- 既存NERの本番置き換え、既存検出候補の自動削除・自動無効化。
- 表記違いの人物の自動関連付け、同一人物推定、住所の推測補完。
- 同一文字列一括マスク仕様の全面変更や、出現箇所ごとの選択UIの新設。
- PDF・画像・音声の直接入力、OCR、新しいファイル取込機能。
- モデル学習・追加学習、クラウドAPIへの送信、クラウドへの自動フォールバック。
- APIキーや新しい利用者アカウントの導入。
- スマートフォン・タブレット、Chrome以外でのPrompt APIの正式対応保証。
- 自動公開、デプロイ、マージ。

## 4. 利用環境とAPI境界

### ENV-01：対象環境

デスクトップ版Chrome 148以降を候補環境とする。実機評価は、少なくとも利用者のWindows 11とChrome安定版の組み合わせ1台で行う。macOSは実機を確保できる場合に追加し、未実施なら報告書に明記する。

Chromeのバージョンだけで利用可と判定しない。`LanguageModel`の存在と、日本語のテキスト入出力を指定した`LanguageModel.availability()`で判定する。セッション作成時も同じ言語・モダリティ条件を使用する。

### ENV-02：準備と非対応時の継続

| API・準備状態 | 画面表示・動作 |
| --- | --- |
| API自体がない、または`unavailable` | 「この環境では追加AI検出を利用できません」。既存検出・手動操作は利用できる |
| `downloadable` | 「初回準備が必要」。利用者の準備ボタン操作からモデル取得を開始する |
| `downloading` | 取得中であることを表示。APIが提供する進捗を表示する |
| `available` | 追加検出を開始できる |
| 取得・初期化失敗 | 再試行できるエラー表示。候補0件や検出完了として扱わない |

モデルはChrome管理であり、アプリの既存NERモデルとは準備状況を別管理する。「準備を中止」はアプリ側の待機・セッション作成の中止を意味し、Chromeのバックグラウンド取得停止までは保証しない。

### ENV-03：実装上の制約

作成時点の公式仕様ではPrompt APIをWeb Workerから呼び出せないため、Window側の薄いアダプターから非同期呼び出しする。既存NER Workerへ無理に組み込まない。推論中も編集・中止等のUI応答を維持し、長い同期ループを避ける。

PoCは安定版の基本APIと`responseConstraint`で成立させる。Web向けのサンプリング設定は別途Origin Trialの対象であるため、`temperature`、`topK`、`samplingMode`やChromeフラグを必須条件にしない。

初回取得量・モデルサイズ・空き容量・ハードウェア条件はChromeに依存する。実装時に公式要件を再確認し、固定したモデルサイズや全端末でのオフライン動作を約束しない。

## 5. 画面・利用フロー

### UI-01：入口

既存の検出操作の近くに「追加AI検出（試験）」を設け、次の短い説明を表示する。

> 端末内AIで見落とし候補を追加確認します。初回はモデルのダウンロードが必要です。結果には誤りがあるため、追加する対象を確認してください。

機能は利用者が明示実行した場合だけ動作し、ページ表示・入力・通常検出から自動起動しない。既存検出が現在の原文に対して正常完了した後に実行できる。既存検出が0件でも正常完了なら実行できる。既存NERが失敗した場合は、再試行を案内し、通常UIからの追加検出は開始しない。評価専用の方式CはこのUI条件とは分離する。

### UI-02：処理中

- 「追加AI検出中：3 / 8区間」のように進捗を表示する。
- 同じ場所に「中止」を表示し、多重実行を防ぐ。
- 原文変更・現在の作業の消去・画面離脱ではジョブを無効化する。
- モデル準備時間と本文検出時間を区別する。

### UI-03：結果確認

結果は通常の有効なマスク対象へ直ちに混ぜず、一時的な確認一覧として表示する。

| 項目 | 表示・操作 |
| --- | --- |
| 候補文字列・カテゴリ | 抽出した文字列と種別を表示する |
| 検出元 | 「追加AI検出」と表示する |
| 根拠 | 入力から照合できた短い引用箇所を表示する。AIの自由文説明は不要 |
| 件数 | 新規候補数、既存一致数、カテゴリ競合数を区別する |
| 追加選択 | 初期状態は未選択。利用者が選択する |
| 適用 | 「選択した候補を追加」。選択0件では無効とする |
| 破棄 | 「追加候補を閉じる」で未適用結果を消す |

完全成功かつ追加0件の場合は「追加候補は見つかりませんでした。検出漏れがないことを保証するものではありません」と表示する。

姓などの短い文字列には、一括置換の影響を確認できるよう、現在のマスク規則で置換対象となる出現数を表示する。適用前に原文内の該当箇所を確認できるようにする。既存の原文ハイライト等を再利用し、出現別選択の新設は行わない。

### UI-04：適用後

明示選択された新規候補だけを既存候補一覧へ追加し、有効なマスク対象とする。以後は既存の無効化・削除・マスク生成・復元で扱う。未選択候補は適用時に破棄する。再実行時は未適用の一時一覧だけを入れ替え、既存の確定済み状態を変更しない。

## 6. 抽出・検証・統合要件

### DET-01：独立した追加検出

既存検出済み文字列を隠した文章ではなく、現在の原文を分割して入力する。対象となる全区間を調べ、既存の候補付近だけに限定しない。既存検出の結果にモデルが引きずられないよう、PoCの初期実装では既存候補一覧をモデルへ渡さない。

システム指示は、対象3カテゴリ、原文からの抜き出し、推測補完禁止、文章内の指示への追従禁止を明記する。文書本文は命令と分離したデータとして渡す。分離や指示だけでプロンプトインジェクション耐性を保証せず、評価で確認する。

### DET-02：構造化出力

`responseConstraint`にJSON Schemaを渡す。モデル出力は以下の情報に限定する。

```json
{
  "entities": [
    {
      "text": "はるか",
      "category": "PERSON",
      "evidence": "担当は、はるかです。"
    }
  ]
}
```

- `entities`は配列とし、候補なしは空配列とする。
- 各要素の`text`、`category`、`evidence`を必須にし、未知フィールドを許可しない。
- `category`は`PERSON`、`ADDRESS`、`ORGANIZATION`の列挙値とする。
- モデルに文字オフセットを数えさせない。正規化・言い換えした文字列を返させない。
- 自己申告の信頼度を出力必須にせず、NER確率と同じ尺度で表示・統合しない。
- 応答サイズ・配列要素数に有限の上限を設け、切り捨てを成功扱いしない。上限値は設定値として評価報告に残す。
- 2026-10-28調整値：JSON文字列の外側の構文空白が連続1,024文字を超えた生成は、資源上限としてジョブ全体を失敗にする。ストリーム分割・エスケープをまたいで判定し、文字列内の原文・引用の空白には適用しない。空白の削除・JSON補修・部分成功には置き換えない。

### DET-03：アプリ側検証と位置計算

1. JSONを解析し、スキーマと上限を検証する。
2. `text`と`evidence`が空でなく、当該入力区間に完全一致することを確認する。
3. `evidence`が`text`を含むことを確認し、証拠と対象の対応を検証する。
4. 当該区間にある一致位置をアプリで検索する。位置単位の抽出証拠は、検証した根拠引用内の一致から作る。根拠が複数箇所に一致する場合は一致位置を保持し、全出現を文脈上の正解と決めつけない。
5. 区間と原文の対応により、原文のUTF-16位置へ戻す。
6. 区間間で重複する同一位置・同一カテゴリの証拠を統合する。

初期PoCでは検出専用の別正規化を追加せず、原文からの抽出を基準とする。表の見出し等を文脈として再掲する場合は、再掲部分を抽出対象外にし、実際の対象部分だけが原文へ対応するようにする。

存在しない文字列、許可外カテゴリ、空文字、位置が対応しない候補は採用しない。形が正しいJSONでも内容の正しさは保証されない。内容検証で棄却が生じた実行は「検証警告あり」とし、正常0件と区別する。生の応答を保存せず、合成データの評価では理由別件数を記録する。

### DET-04：既存候補との統合

| 状況 | 扱い |
| --- | --- |
| 同一文字列・同一カテゴリが既存登録済み | 新しいマスク項目を作らず、既存一致として数える |
| 既存項目が利用者により無効化されている | 無効状態を維持し、追加検出で再有効化しない |
| 同一文字列・別カテゴリが既存登録済み | 既存カテゴリを維持。競合として別表示し、PoCの追加適用対象から除外する |
| 新規文字列が既存項目と包含関係 | 既存ルールに従い共存させ、マスク時は最長一致を使う |
| モデルが別表記を同一人物と示唆 | 自動関連付けしない |
| モデルが既存項目を非個人情報と判断 | 既存項目を削除・無効化しない |

モデルの抽出証拠位置と、最終的な置換位置は別概念として保持・評価する。例えば「森さん」の証拠で「森」を追加した結果、「森を散策」まで置換されるかは、実際の既存マスク規則を通した結果で確認する。追加検出由来の項目にも既存の曖昧姓の保護を適用し、検出元が異なることを理由に保護を迂回しない。保護対象外の文字列による過剰マスクは評価結果へ計上する。

### DET-05：保存との整合

未適用の追加候補・根拠引用・モデル応答・原文位置を既存対応表へ保存しない。適用済み項目は既存保存形式で表現可能な情報だけを保存する。PoCのための保存形式拡張・移行は行わない。

互換方式を次のように固定する。

- メモリ内の検出元に `prompt-api` を追加し、表示は「追加AI検出」とする。手動追加として登録しない。
- v1への保存・変更判定時だけ `prompt-api` を `regex` へ写像し、重複を除く。既存の検出元は保持する。`ner` や `manual` への写像は曖昧姓の一般語保護を迂回するため禁止する。
- 読込形式の許可値は従来の `regex` / `ner` / `manual` のままとする。新しい検出元、根拠、原文位置を暗号化ペイロードにも追加しない。
- 再読込後は追加AI由来を識別できない。`regex` のUI表示を「形式・互換」とし、保存画面で「追加AI検出の検出元は互換保存され、読み直すと形式・互換と表示されます」と説明する。既存の形式検出も同じ表示となる。
- 追加AIのみで登録された曖昧姓は、保存→読込後も一般語保護とマスク範囲を維持する。後から通常検出や手動追加で検出元が増えた場合は、その既存ルールに従う。既存NER側の判定は変更しない。

### DET-06：競合・検証失敗・確認中の変更

- 未登録の同一文字列に複数カテゴリが返った場合もカテゴリ競合とし、その文字列の候補を全て適用対象外にする。返却順で決定しない。
- 不正JSON、必須項目欠落、未知フィールド、型違い、許可外カテゴリ、空または空白だけの文字列、応答・配列上限超過は構造違反としてジョブ全体を失敗にする。
- 型・形式が正常でも原文に存在しない文字列や、根拠と対象の不一致は個別棄却し、警告付き一覧を認める。全件棄却を正常0件と表示しない。
- 適用直前に最新の登録項目と再照合し、新規項目だけを追加する。確認中に手動追加・無効化・関連付けされた既存項目を上書きしない。
- 通常検出の再実行、対応表読込、原文変更、全消去では処理と一時一覧を破棄する。通常検出の正常完了は原文リビジョンごとに管理し、編集で開始条件を失う。0件での正常完了も記録する。
- 削除履歴の永続化・墓標は追加しない。削除済み文字列は次回の明示的な追加検出で再提案され得るが、再び利用者が選択するまで登録しない。

## 7. 長文・セッション・異常系

### RUN-01：文脈を維持した分割

- 文・段落・表の行・JSONのキーと値を可能な範囲で一緒に入力する。
- 調整用データで分割長・重複量を決め、最終評価前に固定する。既存NERの分割値を無条件に流用しない。
- コンテキスト容量はAPIの利用可能量から確認し、システム指示・スキーマ・入力・出力用の余裕を含める。
- 見出し・人名・住所が境界をまたぐデータを評価に含める。大きすぎる単一行・値は位置対応を保って分割する。
- コンテキスト超過で本文が黙って欠落しないようにする。収まらない場合は明示エラーにし、成功扱いしない。

### RUN-02：セッション管理

文書や区間をまたいで会話履歴を蓄積しない。固定システム指示だけを持つセッションのclone等を利用し、各区間を独立して処理する。リソース負荷を抑えるため初期PoCでは逐次実行する。区間完了後と作業終了時に不要セッションをdestroyする。

### RUN-03：中止と古い結果の防止

ジョブIDと原文リビジョンを開始時に保持し、結果反映時に一致を確認する。AbortSignal等による中止に加え、原文変更・全消去・再実行後に返った古いPromiseの結果を破棄する。

タイムアウト初期値は、モデル初回取得を除き、1区間60秒・検出全体300秒とする。設定値を一か所で管理し、評価報告に残す。初回取得・初期化は本文検出と区別して中止・失敗を扱い、本文検出のタイムアウト枠を消費させない。

### RUN-04：部分失敗

小規模PoCでは、全区間の応答取得と構造検証が完了してから一時一覧を表示する。区間の失敗、中止、タイムアウト、応答破損、上限超過では当該ジョブの追加候補を全て破棄し、「追加検出は完了していません」と表示する。既存項目・前回適用済み項目は保持する。

正常応答内の個別候補の内容不一致はDET-03の検証警告として扱い、警告を伴う一覧表示を認める。実行失敗と個別棄却の件数を混同しない。自動の無制限再試行や、失敗を空配列に置換する処理は行わない。

## 8. プライバシーと処理境界

### PRIV-01：端末内推論

モデル呼び出しはChrome組み込みAPIに限定する。クラウドAPI、モデルプロキシ、クラウドへ送るpolyfillを導入しない。非対応・失敗時は追加機能だけを利用不可にする。

### PRIV-02：保存・ログ

入力、プロンプト本文、根拠引用、モデル生応答を、Console、例外ログ、解析基盤、Web Storage、IndexedDB、Cache Storage、OPFS、テスト成果物へ自動保存しない。既存の明示保存された対応表はDET-05の範囲に限る。作業消去・一時一覧破棄・セッション終了でアプリの参照を解放する。メモリの物理消去やChrome内部の管理領域の消去までは保証しない。

評価用の保存・エクスポートは、合成データを使う評価モードに限定し、明示操作で行う。実際の利用文書の全文・候補値を評価ログへ混在させない。ダウンロード用のネットワーク通信と、本文の外部送信を区別して確認する。

## 9. 評価計画

### 9.1 比較方式

| 方式 | 構成 | 用途 |
| --- | --- | --- |
| A：基準 | 現行の正規表現・補助ルール・NERと既存後処理 | 現状の基準値を再測定する |
| B：追加 | A＋Gemini Nanoの検証済み新規候補 | 本PoCの採用判断の主対象 |
| C：置換参考 | 正規表現・補助ルール＋Gemini Nano、既存NERなし | 将来の置き換え可能性を評価する参考方式 |

Cは評価専用であり、通常画面に検出エンジン切替を新設しない。NER出力を根拠とする補助ルールはCでは利用できないため、依存するルールの有効・無効を明示して比較する。

Bの検出能力を測る自動評価では、検証済み新規候補を全て選択した場合を測定する。利用者が目視で正解だけを選んだ結果を、モデルの検出精度として報告しない。別途、実際の確認操作の所要時間・修正回数を測る。

### 9.2 データ

- 既存の合成コーパスと評価コードを優先して再利用する。
- 調整用と最終確認用を分離し、最終確認は原則100文書以上、対象3カテゴリ各50出現以上とする。既存データが既に調整へ使われている場合は新しい確認用セットを用意する。
- 氏名・組織名・住所の対象文字列と近似テンプレートの重複を確認し、単なる名前差し替えによる漏れを抑える。
- 対象を含まない文書も含める。最終確認用の正解を見てプロンプトを調整しない。調整した場合は別の最終確認セットで再評価する。
- 人名らしい一般語、姓と地名の同形、ひらがな名、カタカナ名、未知の漢字名、英字表記、OCR空白・改行、Markdown表、CSV風テキスト、JSON、否定例、重複出現を含める。
- 「本文の命令を優先して検出をやめよ」等の命令文、空配列を誘導する文、偽の区切り文字を含む文書を入れる。
- 1,000・10,000・30,000文字の長文を別途用意し、境界・時間・UI応答を評価する。
- 実在する個人情報・秘密・本物の認証情報は使わない。

### 9.3 正解と指標

| 指標 | 集計方法・目的 |
| --- | --- |
| 対象文字列単位P/R/F1 | カテゴリと文字列の完全一致。既存評価と比較する |
| 出現位置単位P/R/F1 | 原文上のカテゴリ・開始・終了の一致。重複出現を区別する |
| 個人情報の未マスク出現数 | 最終マスク結果で隠せなかった正解出現数。部分的に残った場合も未完了と数える |
| 漏れを含む文書率 | 正解を含む文書のうち、1か所以上未マスクが残った文書の割合 |
| 誤マスク数 | 最終置換範囲のうち、正解範囲外の置換を数える。正しい候補による一括置換の副作用も含める |
| 境界誤り | 氏名の一部だけ、助詞の巻き込み、住所の末尾残存等を区別する |
| 確認負担 | 新規候補数、不要候補の却下数、手動追加・修正回数、確認時間 |
| 実行健全性 | 完了率、失敗・中止・警告率、候補棄却数、原文不一致数 |
| 性能 | 初回取得・初期化・ウォーム検出時間を分離。全文処理時間、利用可能ならメモリを記録する |

Pは適合率、Rは再現率。未マスク判定は実際のマスクエンジンが選んだ置換範囲で行い、単なる文字列再検索では判定しない。カテゴリ違いでも機密部分が隠れた場合は、カテゴリ評価とマスク漏れ評価を分けて記録する。

### 9.4 実行条件

- A/B/Cを同じソースコミット・同じ入力で比較する。
- 調整に使った回数・プロンプト版・JSON Schema版・分割設定・タイムアウトを固定して記録する。
- OS、Chromeの完全なバージョン、CPU、RAM、GPU、モデル準備状態を記録する。モデル版が取得できなければ不明と明記する。
- 最終確認用のB/Cは各3回実行し、平均だけでなく最悪の漏れ数と結果のばらつきを報告する。モデルの再現性を仮定しない。
- 同一実機の実モデル評価は逐次実行する。Chromeによるモデル更新が評価期間内に起きた場合は結果を混在させず、再測定または制約を明記する。
- 失敗文書を除外した精度だけで全体を良く見せない。完了率と、失敗時にAへ戻る利用結果を併記する。
- ブラウザに実モデルが用意できない場合は、モックテストと実測を区別して未完了と記録する。実機準備・手動確認が必要な手順を残す。

### 9.5 採用判断の目安

以下は本要件で設定するPoC用の暫定目安であり、実測済みの効果や製品保証ではない。変更する場合は調整用評価の段階で理由と値を記録し、最終確認の前に固定する。

| 観点 | Bを次段階へ進める目安 |
| --- | --- |
| 漏れ削減 | 最終マスク結果の未マスク出現数を、A比で相対20%以上削減する。3回の最悪値でも達成する |
| カテゴリ | 人名・住所・組織名の各出現単位RecallがAを下回らない |
| 過検出 | 対象文字列単位Precisionの悪化をA比3ポイント以内に抑える。誤マスクの具体例・増分も併記する |
| 確認負担 | 同じ10文書で「Aを手動補完する作業」と「Bの追加候補確認＋手動補完」を各3回測り、中央値が増えない。順序を入れ替え、習熟の影響を記録する |
| 待ち時間 | 評価実機で追加検出のウォーム時間が10,000文字120秒以内、30,000文字300秒以内。各3回の最悪値で判定する |
| 正常完了 | 固定した通常評価セットのBが各回とも全件完了する。意図的な異常系は分離する |
| 安全性・回帰 | 本書の必須受入条件を満たし、既存の無効化・保存・復元・消去を壊さない |

漏れ削減率は`(Aの未マスク出現数 - Bの未マスク出現数) / Aの未マスク出現数`とする。Aが0件なら削減率は算出せず、そのセットだけで追加効果を認定しない。追加候補数が0件で確認時間が短い等の結果も、漏れ削減と合わせて判断する。

Cは参考比較とし、値が良くても本PoC内でNERを置き換えない。目安未達なら「継続検証」「用途限定」「不採用」のいずれかと、理由・残課題を報告する。

確認負担の実測は人による操作で行う。同じ評価者、固定した10文書、漏れと誤マスクを正解に照らして修正し終える完了条件を使い、開始・終了操作と計時区間を記録する。A/Bの順序を交互にし、各3回の結果と習熟の影響を残す。自動操作の所要時間で代替しない。未実施の場合は採用判断を保留とする。
