# マスク対応表の実装確認メモ

## 2026-10-06 承認済み修正後の状態

- 保存対象・暗号・一覧用平文メタデータの境界は維持する。更新ごとに`{mapping-id}@r{revision}.mapping.enc`へ暗号化し、一時ファイルの復号と正式ファイルの読み戻しを検証する。IDに使えない`@`で区切り、別IDの旧ファイル名との衝突を防ぐ。旧ファイルを上書きせず、旧一覧と参照先暗号化ファイルを対で保持する。旧固定ファイル名は読込可能。
- 主一覧の欠落・破損時は有効なバックアップから読込専用で利用し、保存・個別削除を停止する。両一覧の破損やアクセス拒否を空一覧と扱わない。自動補正・移行はしない。
- 起動時に残存状態を確認し、管理画面で暗号化ファイル・両一覧から未参照のファイル・一時ファイルの件数を示す。旧版・孤立・一時ファイルを自動削除しない。
- Web Locksで読込・保存・削除を排他制御し、ロック取得後にrevisionを検査する。未対応時は読込専用。
- 個別削除はバックアップから対象IDを除外した後、全revisionと対象一時ファイルを削除し、最後に主一覧を更新する。全件削除も復旧一覧を先に無効化する。欠落以外の削除失敗を通知し、再試行を可能にする。途中中断後は欠損表示となり得るが、バックアップから削除対象を復活させない。
- 保存形式v1ではID・正規化対象・トークンをそれぞれ一意にする。解除前の情報を保持できない関連付けを保存・読込で拒否し、既存ファイルは保持する。関連付けは現在の作業内で利用でき、解除後は保存できる。関連付けの永続化には別途要件・スキーマ改訂が必要。
- 読込時は復元欄を閉じる。関連付け解除時に元の対応情報が欠落していれば推測補正しない。

[故障注入テスト](../src/domain/mapping/opfsRepository.test.ts)、[Reducerの通し状態遷移](../src/app/reducer.test.ts)、[実OPFSブラウザ試験](../e2e/mapping-storage.spec.ts)を追加した。ブラウザ強制終了・端末故障に対する完全な原子性や永続保持は保証しない。復旧一覧を正式一覧へ昇格するUI、孤立ファイルの個別救出・外部バックアップは未実装。復旧時は読込専用で元ファイルを保持する。

## 修正前の監査記録

以下は修正前の記録であり、現在の未達事項ではない。

確認日：2026-10-06（ソースと既存テストの再照合。実OPFSのブラウザ操作は今回未実施）

本書は、[マスク対応表のローカル保存要件](local-work-history-requirements.md)、[画面設計仕様](ui-design.md)と、現在の実装との差異を明示するためのメモである。要件を置き換えるものではなく、未達項目を実装済みと誤認しないために使用する。

### 実装と一致していた範囲

- `originalText`、`maskedText`、外部回答、復元結果、画面状態を永続化せず、有効なマスク対応表だけを保存する。
- 対応表本文をAES-GCM、PBKDF2、gzipで暗号化し、EnvelopeヘッダーをAADで認証する。
- 平文インデックスには対応表ID、対応表名、作成・更新日時、暗号化ファイル名、フォーマットバージョン、リビジョンだけを保持する。
- 管理一覧、別ダイアログでのパスフレーズ入力、上書き／新規保存、個別削除、全削除、現在の作業との紐付け解除を実装している。
- 保存時の一時ファイル検証、インデックスのバックアップ、Web Locksまたはリビジョンによる競合検出を実装している。

### 修正前の差異・未達項目

### 対応表を開いた後の復元セクション

要件では、対応表を開いた後に復元セクションを閉じることとしている。現在の`loadMaskMapping`は外部回答が入力中の場合の読み込みを拒否し、外部回答・復元結果を復元しないが、`restoreExpanded`を明示的に`false`へ戻していない。復元セクションを開いた状態で対応表を開いた場合、この受入条件は未達である。

### 孤立ファイル・一時ファイルの起動時検出

要件では、インデックスにない暗号化ファイルを孤立ファイルとして保持し、一時ファイルを未完了処理として検出して削除候補にすることとしている。現在のRepositoryはインデックス項目に対応するファイルの欠損を`missing`として表示し、インデックス破損時にバックアップを試行するが、起動時に`mappings`と`temporary`を走査して孤立ファイル・一時ファイルを一覧へ提示する処理は実装していない。

### Repository層のテスト

暗号、スナップショット、Reducer、ダイアログのテストは存在する。一方、OPFS APIを模したRepository結合テストは未整備であり、インデックス破損、バックアップ復旧、書き込み失敗時のロールバック、孤立・一時ファイル検出、Web Locks非対応時の競合を自動検証できていない。

### 保存対応の一意性と関連付け

[保存要件4節](local-work-history-requirements.md)とFR-18Aでは対象・トークンの一対一対応を求め、1つのトークンに複数対象文字列がある場合は保存を中止する。現行`validateMappingUniqueness`は、`relationId`、カテゴリ、復元文字列が同じなら複数対象の同一トークンを許可し、関連付けを保存できる。さらに`relationId`がどちらも未設定であってもカテゴリ・復元文字列が同じなら同一トークンを許す。これは要件との差異であり、保存要件を実装に合わせて緩めない。

### 保存後に開いた関連付けの解除

`snapshot.ts`は共通トークン・代表復元文字列・`relationId`を保存するが、関連付け前の`relatedOriginalToken`と`relatedOriginalRestorationText`を保存せず、`reapply.ts`も復元しない。保存、現在の作業消去、対応表読み込み、関連付け解除の順では、解除後も代表表記が残る。グループ全体の解除では各項目が同じ既存一覧を基にトークンを生成するため、別表記へ同じ新規トークンが割り当たる可能性がある。AC-07bの元の個別トークン・復元表記へ戻す条件を満たさず、復元結果の取り違えにつながるため優先して対処する。

### 修正前の取り扱い

上記の未達項目が解消されるまで、保存対応の一意性、保存後の関連付け解除、障害復旧、復元セクション閉鎖の受入条件を「達成済み」と扱わない。次の実装では関連付け保存の許可範囲を先に確定し、復元結果を取り違えないことを優先する。続いてReducerの復元セクション状態、Repositoryの起動時復旧と結合テストを確認する。全体の照合範囲は[実装・文書の照合結果](implementation-status.md)を参照する。
